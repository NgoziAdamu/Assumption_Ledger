### 主要证据与单点结果

- **U：impl-020 conversation part aggregates。** P 为每个 conversation 都有匹配 part。agent 可见数据有 6,703 个 conversation，其中 5,726 个无 part；event 39/40 已见 conversation 6,703 与 aggregates 977 的行数差。CS 上游没有匹配 part。独立改动驱动连接一处后，不一致规模从 6,703 行/26,812 格降至 0，L0 整表匹配，标记“证据曾出现但被忽略”。C/U 边界另外记录规则问题。
- **I：impl-015 invoice_line 与 impl-018 order。** 前者 event 17 的正确映射在 event 21 被覆盖，候选 `sales_item_item_id` 20,000 条非空且全部匹配 item，所选 `item_id` 全空；单改 40,000 行/760,000 格降至 0。后者 event 57 明确写出应保留 foreign key 的正确意图，但 order 留下 `id as account_id`；单改 3,000 行/3,000 格降至 0。I 的依据来自轨迹和代码意图，不仅是 gold 选列。
- **D：impl-015 payment_line、vendor。** 存在 invoice ID、名称候选，代码直接整列 NULL 占位，未见判断；分别单改至 L0 匹配。event 73 有跨表类型化 NULL 策略，因此均加“已披露”，四档为“只有通用策略说明”。
- **C 与 O 可同时参与。** Workday 两张 overview 的主因是 gold grade 正则不提取普通数字（O）；employee 的 compensation JOIN 重复度、position 的组织维度缺失分别是 C 参与因素。按行数优先选主因，没有因为某项格数改善更大就改变排序。Greenhouse job enhanced 的主因是 `current_date`/`current_timestamp` 用法 C，另有 prospect 转 VARCHAR 的 C 与 gold 比率 NULL 行为的 O。
- **A 按代码位置拆开。** Salesforce contact 各个字段的 NULL/空串表达式、lead 各个默认与清洗表达式都独立重跑。Intercom company metrics 的三个 contacts 默认表达式分别单改，改善并列且类别均为 A，故主因直接记 A，未记“多因并列”。Apple session 的三处日期过滤表达式分别记录，未捆绑。
