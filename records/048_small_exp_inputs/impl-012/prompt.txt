**Implementation Requirements:**
1. **Strictly Adhere to Configuration**:
    * All SQL logic and dependencies must be written strictly according to the `staging`, `intermediate`, and `marts` hierarchy defined in the YAML configuration files.

2. **File and Directory Structure**:
    * SQL files must be created in the corresponding level subdirectories (e.g., `sql/staging/`, `sql/intermediate/`, `sql/marts/`).
    * Strictly follow predefined file naming conventions and coding styles.

3. **Use Pure DuckDB Syntax**:
    * All SQL code must be compatible with DuckDB.
    * **Do NOT** end SQL statements with a semicolon (`;`) at the end of the file.

4. **No dbt Syntax**:
    * You must reference upstream tables directly using the `schema.table_name` format.
    * **Do NOT** use the dbt `ref()` function.

    **Examples**:
    * **Correct ✅**:
```sql
    with account_base as (
    select *
    from staging.stg_salesforce__account
    where not is_deleted
    ),

    account_enriched as (
    select
    account_id,
    ...
```

* **Incorrect ❌**:
```sql
    WITH accounts AS (
    SELECT *
    FROM {{{{ ref('stg_salesforce__account') }}}}
    ),
    contacts AS (
    SELECT *
    FROM {{{{ ref('stg_salesforce__contact') }}}}
    ),
    ...
```
Output Standard: Ensure the generated SQL files can be successfully executed by run.py to produce high-quality data results that meet business requirements.

modeling_spec:
  purpose: "Transform staging data into business-ready models that support marketing analytics, lead management, and campaign performance analysis. This phase applies complex business logic, creates reusable intermediate models, and produces final analytical marts."
  
  design_principles:
    intermediate_purpose: "Create reusable, business-centric data models that implement complex logic and serve as building blocks for multiple downstream marts"
    marts_purpose: "Produce analysis-ready fact and dimension tables optimized for BI tools and analytical queries"
    grain_importance: "Every model must have an explicitly defined grain that determines the level of detail and uniqueness of each row"
    naming_convention: "int_marketo__[business_concept] for intermediate models, marketo__[business_entity] for marts"

  intermediate_models:
    - name: int_marketo__lead
      description: Lead dimension with merge/delete flags derived from activity tables; all leads from staging are retained (no filtering)
      grain: One row per input row in staging.stg_marketo__lead; duplicates on lead_id are preserved
      source_models:
      - staging.stg_marketo__lead
      - staging.stg_marketo__activity_merge_leads
      - staging.stg_marketo__activity_delete_lead
      business_logic: '- Start with all rows from staging.stg_marketo__lead (no filtering or deduping in this model). - Build deleted_leads as the distinct set of lead_id from staging.stg_marketo__activity_delete_lead. - Build unique_merges from staging.stg_marketo__activity_merge_leads by: - Grouping by lead_id and concatenating distinct merged_lead_ids separated by ", ". - Null policy: null merged_lead_ids are ignored; if no non-null values exist for a lead, the result is null. - Ordering: no explicit ordering is applied during concatenation, so the sequence is not guaranteed. - Left join deleted_leads and unique_merges to the lead base on lead_id. - Compute flags: - is_deleted = TRUE if a matching deleted_leads.lead_id exists, else FALSE. - is_merged = TRUE if merged_into_lead_id is not null, else FALSE. - Select all original lead attributes unchanged (formatting preserved), plus is_deleted, merged_into_lead_id, and is_merged.'
      columns:
