# DAComp DE-Impl 错误归因标注手册（v2，冻结版）

版本：v2，2026-10-29。根据试标 30 张（impl-001～030 各 1 张）修订后冻结，用于全量标注。修订记录见第 10 节。

冻结的含义：全量标注期间不再修改类别定义和判定门槛。只允许补充操作性说明（不改变任何已标结果的那种），补充时记录日期和理由。如果确实必须改定义，所有已标的表按新定义重标。

## 1. 要回答的问题

每张被判错的表，回答两个问题：
1. **它为什么和标准答案不一致？**（第 3～5 节）
2. **agent 有没有把相关的不确定性说出来？**（第 6 节）

- 标注对象：`records/013_statuses.csv` 中状态为"待标注"的表。
- 判错按官方评分，不重新定义"对错"。中间层及以后按 CS 口径：上游一律用标准答案，只看这一张表自己。
- 没有预期的类别分布。每个类别都需要同等强度的证据。

## 2. 每张表要做的事

1. **描述错在哪里**：说清楚 agent 的输出和标准答案差在哪、差异从 SQL 的哪一处来。
2. **依据**：契约哪几行、两边 SQL 哪几行、差异里的哪些数字、轨迹哪几个事件。
3. **agent 有没有看过能判断这件事的东西**：数据或文档，附事件编号。以 agent 实际看到的为准，轨迹里被截断的输出不算看过。
4. **查询和重跑**（第 7 节）。
5. **类别和把握**：主要原因（一个类别，或"多因并列"），参与因素，标记。把握分高、中、低。拿不准就写原因，判断不了标 X。
6. **不确定性是否说出**（第 6 节）。

## 3. 类别

**U 未核实假设**：四个条件同时满足。
1. 能写出 agent 代码依赖的一句关于数据的话 P，例如"每个客户 ID 只出现一次"。
2. P 实际上不成立。证据可以是数据查询，也可以是契约、数据字典、字段注释等文字材料。
3. agent 整个过程中没看过任何足以判断 P 的东西。证据出现过但 agent 没理会的，仍归 U，加标记"证据曾出现但被忽略"。
4. 只改掉依赖 P 的那部分、其余不动，重跑这张表：完全对上；或在两位小数这一档下完全对上；或不一致的规模减少至少一半（规模怎么数见第 5 节）。作为参与因素或多因并列中的一项时，按第 4、5 节的放宽要求。

补充：
- agent 因为误以为数据有问题（例如以为源表不存在，实际没问题）才换表或填空值，归 U。
- 契约没要求处理，但数据违反了这一列本身含义决定的硬约束（例如纬度超出正负 90 度、计数为负、百分比超过 100），agent 没发现、没处理，归 U。如果只是业务上要不要剔除的选择（值本身合法），归 A。
- 契约没给源列对应关系、agent 选了某一列：只有 agent 当时能看到的数据给出了明确结论（例如所选列与相关表完全匹配不上，另一列能匹配），才归 U；否则归 A。不能用标准答案的选择作为对错依据。

**D 悄悄降级**：agent 没有误解数据，而是直接占位、整列填空值、换表、输出空表，然后宣称完成。轨迹里找不到 agent 对数据有任何判断的痕迹，就归 D。原始表里有看得出来的候选列，agent 却没做任何判断就填了空，也归 D。agent 在报告里写明了占位的，仍归 D，加标记"已披露"。

**C 没照契约做**：契约直接规定了怎么做（取哪一列、怎么过滤、用什么表达式），agent 没照做或理解成了别的意思。契约给出了可以在评测引擎中直接执行的写法时，按字面执行的效果为准，不推测"本意"。

C 和 U 的界线：契约**规定了做法**而 agent 没照做，归 C；契约**只说明了数据的性质**（例如"项目可能缺失"、"可能重复"），agent 的代码却依赖相反的性质，归 U，加标记"证据曾出现但被忽略"。

**A 歧义**：契约本身没写清楚，数据也帮不上忙，agent 选了一种做法，标准答案选了另一种。契约没写清、但查数据就能定下来的，归 U。原始表里根本没有对应的列、填 0 还是填空契约没说，归 A。描述时只说"差异取决于契约没定的选择"，不说 agent 做错。

**I 代码写错**：agent 的想法是对的，代码没写出这个想法。想法可以从思考、报告中看出，也可以从代码自身的明确证据看出（例如同一个映射里先写了正确的列，后面又被覆盖）。看不出想法时不归 I。

**O 其他**：差异不是 agent 处理数据的方式造成的，换个评测条件就算对。包括：标准答案与契约自相矛盾（例如 agent 按契约的类型或唯一性输出，标准答案没有）；契约明确允许任意顺序、差异只在并列项的先后顺序（需用诊断查询确认其余内容一致）。措辞保持中性，只描述事实，不评价 benchmark。

**X 无法判定**。只用于确实看不出原因的情况，不用于"原因清楚但不满足某个门槛"。

**不可评估**：这张表依赖的原始表，agent 留存库与初始库一致、而标准答案库不同（标准答案用的原始数据本身就不同），经诊断确认后标"不可评估"，不归任何类别。如果是标准答案库与初始库一致、agent 留存库不同（agent 运行中改动了原始数据），不属于不可评估，照常标注，并在轨迹里找出改动的步骤和原因。

## 4. 参与因素和标记

- **参与因素**：主要原因之外的错误点，只改这一处重跑，规模有所减少（不要求减少一半），记为参与因素并写明类别。U 作为参与因素需满足 U 的前三个条件。
- 只改这一处、规模完全没变的，不算参与因素。如果它确实是 agent 没核实就依赖的假设，加标记"存在未核实假设，但不是判错原因"。
- 其他标记："证据曾出现但被忽略"、"已披露"。

## 5. 不一致的规模和主要原因

- 规模先按**行**数：仅 agent 有的行 + 仅标准答案有的行 + 共同键中至少一列不同的行。比较时使用包含评测键在内的整表口径。
- 每个错误点单独修一次、分别重跑，规模减少最多的是主要原因。
- 按行数比不出时，改按**格子**数：共同键中值不同的格子数，加上仅一侧行的行数乘以比较列数。
- 按格子数仍然并列的，主要原因记为"多因并列"，逐项列出每个并列项的类别。并列项各自按类别标：并列项中的 U 只需满足 U 的前三个条件、且单修后减少的规模与其他并列项相同，不要求减少一半。
- 所有并列项类别相同时，主要原因直接记为该类别，不记"多因并列"。

## 6. 不确定性是否说出（每张表都填）

针对本表差异所涉及的那个选择或假设，agent 有没有把它说出来，分四档：

1. **针对本表的具体说明**：思考或最终报告中，明确针对本表这一处说了有多种理解、数据可疑、或说明了选择了哪种做法及原因。附事件编号和原句。
2. **只有通用策略说明**：只有适用于很多表的笼统说法（例如"转换失败的值会变成空"），没有点到本表这一处。附事件编号和原句。
3. **看到了但没提**：轨迹显示 agent 看到了相关信息（列清单、样例、报错、行数），但没有任何说明。附事件编号。
4. **没有迹象**。

只记录事实，不因此改变类别。一张表有多个错误点时，针对主要原因填；多因并列时，每个并列项分别填。

## 7. 查询和重跑

- **核实查询**：只查 agent 当时能看到的数据，用于检验 P 是否成立。每张表不超过 5 条。记录条数和核实代价档：一条查询、多条查询、需要查业务说明、判断不了。
- **诊断查询**：可以查标准答案，只用于定位差异、确认是不是 O 或不可评估。不计入那 5 条。
- **重跑**：只改指定的一处，其余字节不动，在私有副本中执行。与标准答案按 L0–L3 比较，报告行数口径和格子数口径的规模、每列不一致数、整表首次匹配档位，并列出改动前的同口径数字。
- 涉及运行时间的表，基线和所有修改使用同一个固定时间，作为共同控制，不算单独原因。
- staging 的原始数据一律用 agent 留存库里的 raw 表。intermediate 及以后按 CS 口径，上游用标准答案。
- 数据库一律只读打开原件。

## 9. 规则问题

遇到本手册覆盖不了、或者两种读法都说得通的情况，按你认为最合理的方式标，并在结果末尾"规则问题"一节写明：是哪张表、哪两种读法、你选了哪种、为什么。不要自行修改本手册。

## 10. 修订记录
