# DAComp DE-Impl 错误归因标注手册（v1）

版本：v1，2026-10-29。在 v0 基础上，根据试标第一批（impl-001～010）暴露的问题修订，修订记录见第 9 节。试标完成后可能再修订。

## 1. 要回答的问题

每张被判错的表，回答一个问题：**它为什么和标准答案不一致？**

- 标注对象：DAComp DE-Impl 30 题中，官方评分判错、且经过格式和运行日期筛查后仍不一致的表（见 `records/013_statuses.csv` 中状态为"待标注"的行）。
- 判错按官方评分，不重新定义"对错"。中间层及以后按 CS 口径：上游一律用标准答案，只看这一张表自己。
- 没有预期的类别分布。每个类别都需要同等强度的证据。

## 2. 每张表要做的事

先用大白话描述，再考虑类别。

1. **描述错在哪里**：说清楚 agent 的输出和标准答案差在哪、差异从 SQL 的哪一处来。
2. **依据**：契约哪几行、两边 SQL 哪几行、差异里的哪些数字、轨迹哪几个事件。
3. **agent 有没有看过能判断这件事的东西**：数据或文档，附事件编号。以 agent 实际看到的为准，轨迹里被截断的输出不算看过。
4. **查询和重跑**（见第 6 节）：查询原文和结果、重跑的具体改法和结果。
5. **类别和把握**：主要原因一个类别（或"多因并列"，见第 5 节），参与因素可多个，加标记（见第 4 节）。把握分高、中、低。拿不准就写原因，判断不了标 X。

## 3. 类别

**U 未核实假设**：四个条件同时满足。
1. 能写出 agent 代码依赖的一句关于数据的话 P，例如"每个客户 ID 只出现一次"。
2. P 实际上不成立。证据可以是数据查询，也可以是契约、数据字典、字段注释等文字材料。
3. agent 整个过程中没看过任何足以判断 P 的东西。证据出现过但 agent 没理会的，仍归 U，加标记"证据曾出现但被忽略"。
4. 只改掉依赖 P 的那部分、其余不动，重跑这张表：完全对上；或在两位小数这一档下完全对上；或不一致的规模减少至少一半（规模怎么数见第 5 节）。

补充：
- agent 因为误以为数据有问题（例如以为源表不存在，实际没问题）才换表或填空值，归 U。
- 契约没要求处理，但数据违反了这一列本身含义决定的硬约束（例如纬度超出正负 90 度、计数为负、百分比超过 100），agent 没发现、没处理，归 U。查一下数据就能发现。如果只是业务上要不要剔除的选择（值本身合法），归 A。
- 契约没给源列对应关系、agent 选了某一列：只有 agent 当时能看到的数据给出了明确结论（例如哪一列能和相关表对上），才归 U；否则归 A。不能用标准答案的选择作为对错依据。

**D 悄悄降级**：agent 没有误解数据，而是直接占位、整列填空值、换表、输出空表，然后宣称完成。轨迹里找不到 agent 对数据有任何判断的痕迹，就归 D。原始表里有看得出来的候选列，agent 却没做任何判断就填了空，也归 D。agent 在报告里写明了占位的，仍归 D，加标记"已披露"。

**C 没照契约做**：契约直接规定了怎么做（取哪一列、怎么过滤、用什么表达式），agent 没照做或理解成了别的意思。契约给出了可以在评测引擎中直接执行的写法时，按字面执行的效果为准，不推测"本意"。

C 和 U 的界线：契约**规定了做法**而 agent 没照做，归 C；契约**只说明了数据的性质**（例如"项目可能缺失"、"可能重复"），agent 的代码却依赖相反的性质，归 U，加标记"证据曾出现但被忽略"。

**A 歧义**：契约本身没写清楚，数据也帮不上忙，只能问人。契约没写清、但查数据就能定下来的，归 U。原始表里根本没有对应的列、填 0 还是填空契约没说，归 A。

**I 代码写错**：agent 的想法是对的，代码没写出这个想法。想法可以从思考、报告中看出，也可以从代码自身的明确证据看出（例如同一个映射里先写了正确的列，后面又被覆盖）。看不出想法时不归 I。

**O 其他**：差异不是 agent 处理数据的方式造成的，换个评测条件就算对。包括：标准答案与契约自相矛盾；契约明确允许任意顺序、差异只在并列项的先后顺序（需用诊断查询确认其余内容一致）。措辞保持中性，只描述事实，不评价 benchmark。

**X 无法判定**。

**不可评估**：确认标准答案所用的原始数据与 agent 拿到的不同时，这张表不归任何类别，标为"不可评估"，写明诊断依据。

## 4. 参与因素和标记

- **参与因素**：除主要原因之外的错误点，只改这一处重跑，不一致的规模有所减少（不要求减少一半），记为参与因素，并写明类别。
- 只改这一处、规模完全没变的，不算参与因素。如果它确实是 agent 没核实就依赖的假设，加标记"存在未核实假设，但不是判错原因"。
- 其他标记："证据曾出现但被忽略"、"已披露"。

## 5. 不一致的规模和主要原因

- 规模先按**行**数：仅 agent 有的行 + 仅标准答案有的行 + 共同键中至少一列不同的行。比较时使用包含评测键在内的整表口径。
- 每个错误点单独修一次、分别重跑，规模减少最多的是主要原因。
- 如果按行数比不出（例如两处错误各自都让所有行出错，单修任何一处行数都不变），改按**格子**数比：共同键中值不同的格子数，加上仅一侧行的行数乘以比较列数。
- 按格子数仍然并列的，主要原因记为"多因并列"，列出并列的各类别。

## 6. 查询和重跑

- **核实查询**：只查 agent 当时能看到的数据，用于检验 P 是否成立。每张表不超过 5 条。记录条数和核实代价档：一条查询、多条查询、需要查业务说明、判断不了。
- **诊断查询**：可以查标准答案，只用于定位差异、确认是不是 O 或不可评估。不计入那 5 条。
- **重跑**：只改指定的一处，其余字节不动，在私有副本中执行。与标准答案按 L0–L3 比较，报告行数口径和格子数口径的规模、每列不一致数、整表首次匹配档位，并列出改动前的同口径数字。
- staging 的原始数据一律用 agent 留存库里的 raw 表（agent 运行时可能改过原始表，见 `records/013_raw_impl-NNN.json`）。intermediate 及以后按 CS 口径，上游用标准答案。
- 数据库一律只读打开原件。

- 精简材料包：`records/013_packages/013_impl-NNN_*.md`。
- 轨迹原文：`traces/dacomp_deimpl_prev.tar.gz`，每题事件在 `dacomp_deimpl_prev/runs/20261025_de_official_batch_01/impl-NNN/agent/.events/sessions/<id>/events/<n>.json`。

## 8. 规则问题

遇到本手册覆盖不了、或者两种读法都说得通的情况，按你认为最合理的方式标，并在结果末尾"规则问题"一节写明：是哪张表、哪两种读法、你选了哪种、为什么。不要自行修改本手册。

## 9. 修订记录

v1（2026-10-29），根据试标第一批，经用户确认：
1. 参与因素只要求规模有所减少，不要求减少一半。
2. 新增第 5 节：规模先按行数，比不出改按格子数，仍并列记"多因并列"。
3. 新增 C 与 U 的界线：契约规定做法归 C，只说明数据性质归 U 并加"证据曾出现但被忽略"。
4. 契约给出可执行写法时按字面效果为准。
5. 违反列本身硬约束的未处理数据归 U；业务取舍归 A。
6. 原始表有候选列却不判断直接填空归 D；根本没有对应列归 A。
7. 标准答案所用原始数据与 agent 的不同，标"不可评估"。
8. 并列项顺序不确定且契约允许任意顺序的，归 O。
9. 代码自身的明确证据可以作为"代码写错"的意图依据。
10. 没有源列对应关系时，只有 agent 可见的数据给出明确结论才归 U，否则归 A。
11. 删除 v0 存入仓库时末尾多出的一句表达类别期望的话。
